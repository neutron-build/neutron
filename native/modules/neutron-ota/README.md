# Native OTA integration

This module supplies the iOS and Android persistence/cryptography/boot implementation used by `createNativeOTAAdapter()`. Native compilation, codegen, installed-app tests and device acceptance must pass before release; source presence is not those results.

Supported source targets: React Native 0.76, iOS 15.1+, Android API 24+ with pinned Tink Android 1.13.0 `Ed25519Verify` (no assumption that a platform JCA provider supports Ed25519). iOS uses CryptoKit Ed25519. Keys are base64 raw 32-byte Ed25519 keys or Ed25519 SPKI DER/base64/PEM (12-byte `302a300506032b6570032100` prefix); signatures are base64 64-byte Ed25519 signatures over UTF-8 `canonicalManifest()`. No secret is embedded in this package. The native host provisions trust, channel and runtime; JS cannot change that trust.

Add the workspace package as an app dependency and run the host's ordinary RN autolinking/codegen. `package.json` specifies `NeutronOTASpec`, `modules`, `src`, and Android package `org.neutron.ota`; `src/NativeNeutronOTA.ts` is the sole codegen input. CocoaPods discovers `NeutronOTA.podspec`; Android uses `NeutronOTAPackage` and the RN Gradle plugin. Generated headers/classes come from RN codegen, not checked-in guessed output. Verify Swift selectors/ObjC generated protocol and Android generated spec against the pinned RN compiler before packaging.

Before constructing a bridge or loading JS, configure `NeutronOTAStore.shared` using app-owned storage and a directory containing the original `index.jsbundle` plus packaged assets. The root must derive from the OS application container; initial OS container aliases are resolved once, then stage/receipt/bundle descendants refuse links. Every cold launch must call `selectBundleForBoot()` and use its returned URL/file as the RN bundle loader. Do not cache a bundled URL as an alternative loader. On iOS an AppDelegate's `sourceURL(for:)` / `bundleURL()` should return the store's selected URL, including reloads. On Android a legacy `ReactNativeHost.getJSBundleFile()` must return the selected path; `reload()` clears that host and recreates its Activity. A bridgeless ReactHost fixes its loader at construction: configure a native reload owner which destroys that host, constructs its replacement from the returned selection, then reattaches the Activity. Unsupported host reloads reject rather than recreating a window and claiming success.

Only one native store may own the app-private directory; an OS file lock serializes processes. Boot marks an attempted launch durably before JS; an unconfirmed prior attempt counts as a crash on the next process. Three failures select last-good before JS. `markSuccessfulLaunch()` confirms the current launch and records last-good. The monotonic build watermark survives rollback. An interrupted stage is never selected. An immutable bundle and its authenticated receipt are synced before atomic pending metadata publication. Orphaned stages/bundles from interrupted publication are retained and require explicit discard/new identity; they are not silently promoted. This is process-kill recovery; physical power-loss validation remains a separate gate.

The assembled bundle digest is SHA-256 over an inventory sorted by UTF-8 relative path bytes. Each record is `path + NUL + lowercase SHA256(file bytes) + LF`, encoded as UTF-8. Empty directories do not contribute. The inventory includes unchanged files; deleted files disappear. File hashing streams in 64 KiB blocks; assembled content is capped at 64 MiB and 4096 files. JS chunks are bounded and cross the native module as base64; this transport is not zero-copy. Publication reauthenticates signed fields, validates every chunk and final digest under the native lock, and CAS-checks the durable build watermark. The running bundle is never modified.

Host-source tests: `node native/scripts/test-platform-host.cjs` from the repository root after normal dependency setup (or `node scripts/test-platform-host.cjs` in native). The separate iOS XCTest and Android process harness sources exercise actual stores and kill/relaunch behavior when integrated into installed test apps. A shared JS fixture is not native persistence evidence.

Acceptance target setup: copy `tests/fixtures/vector.json` and the `packaged` folder as iOS test/app resources. Add `tests/ios/NeutronOTAStoreTests.swift` to a store unit-test target and `NeutronOTAProcessAcceptance.swift` to its UI-test target; `OTAProcessFixtureApp.swift` belongs only to a separate acceptance application. On Android, add the two `tests/android/*.kt` sources to a separate debug acceptance app (the `AndroidTestCase` source goes to androidTest), add `tests/fixtures` as its assets directory, and explicitly register the fixture Activity as exported only in that debug acceptance app. Use a fresh app data directory; the driver deliberately does not erase existing data. Run `process_acceptance.py --serial SERIAL --app ACCEPTANCE_APP_ID`. Neither harness builds, installs or deletes production app data by itself. After these storage tests, separately test actual Hermes/Fabric module lookup, bridge reload, native loader selection and healthy confirmation in the RN host; the UIKit/Activity storage harness does not establish those outcomes.
