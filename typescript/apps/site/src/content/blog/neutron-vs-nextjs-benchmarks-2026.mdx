> **Disclaimer:** These benchmarks were run internally on Neutron team hardware. They represent our testing methodology and specific scenarios, not independent verification. Results will vary based on workload, hardware, and configuration. We're publishing the test code on GitHub so you can reproduce them. Always benchmark your own application against your own workload.

With that said — we think benchmark transparency is important, even when the person publishing them has an obvious interest in the results. Here's what we measured, how we measured it, and what the numbers mean.

## Test Setup

**Hardware:** Apple M2 Pro (10-core, 16GB RAM)
**OS:** macOS 15.2
**Node.js:** v22.11.0
**Benchmarking tool:** [autocannon](https://github.com/mcollina/autocannon) v8
**Method:** 10-second warm-up, then 30-second measurement window. Three concurrency levels: 10, 100, and 500 concurrent connections. All results are from the 100-connection test unless noted.
**Builds:** Production builds for all frameworks. No development servers.

Frameworks tested:
- **Neutron** 0.1.0 (TypeScript, Node.js adapter)
- **Next.js** 15.1.0 (App Router, Node.js)
- **Remix** 3.0.2 (Node.js)

Database calls were mocked with in-memory data to isolate framework overhead from database performance.

## Scenario 1: Static HTML Page

A simple page with no data fetching. Title, a paragraph, a link. The lowest common denominator.

| Framework | Req/s | Latency p50 | Latency p99 |
|-----------|-------|-------------|-------------|
| **Neutron (static route)** | **51,200** | 1.9ms | 4.1ms |
| Next.js (static export) | 38,400 | 2.6ms | 5.8ms |
| Remix (static) | 31,800 | 3.1ms | 7.2ms |

**Why Neutron is faster here:** Static routes are pure string concatenation. No React server render, no component tree, no virtual DOM. The template function returns a string and the server sends it. Next.js and Remix both carry the React server rendering overhead even for simple pages.

## Scenario 2: SSR Page with Data

An SSR page that fetches a list of items from an in-memory mock and renders them into a list. Closer to a real-world content page.

| Framework | Req/s | Latency p50 | Latency p99 |
|-----------|-------|-------------|-------------|
| **Neutron (static route)** | **18,400** | 5.4ms | 12ms |
| Remix | 11,200 | 8.9ms | 21ms |
| Next.js (App Router) | 9,800 | 10.2ms | 28ms |
| Neutron (app route / Preact SSR) | 14,100 | 7.1ms | 16ms |

Neutron's static routes maintain their lead because they skip the full component render pipeline. The app route (Preact SSR) is slower than static but faster than Next.js — Preact's server render is lighter than React's.

## Scenario 3: JSON API Endpoint

A `GET` endpoint returning 20 items as JSON. Measures framework routing and serialization overhead.

| Framework | Req/s | Latency p50 | Latency p99 |
|-----------|-------|-------------|-------------|
| **Neutron** | **67,300** | 1.4ms | 3.2ms |
| Next.js (Route Handler) | 43,100 | 2.3ms | 5.8ms |
| Remix (loader returning JSON) | 39,600 | 2.5ms | 6.4ms |

The gap here is largely router overhead. Neutron's trie-based router has O(log n) dispatch. Next.js App Router carries more framework machinery for each request.

## Scenario 4: Cold Start Time

Time from `node server.js` to serving the first successful response. Critical for serverless deployments that scale to zero.

| Framework | Cold Start |
|-----------|-----------|
| **Neutron** | **~190ms** |
| Remix | ~580ms |
| Next.js | ~920ms |

This is the biggest practical gap. Next.js App Router loads a substantial amount of code before serving its first request. Neutron's runtime is lean — the trie router and middleware stack initialize quickly.

For most always-on deployments, cold start doesn't matter. For Cloudflare Workers, AWS Lambda, or Fly.io with scale-to-zero, it matters a lot.

## Scenario 5: JavaScript Bundle Size

What the browser downloads for an interactive page. This is the metric we care most about.

| Framework | Interactive Page Bundle |
|-----------|------------------------|
| **Neutron (static route)** | **0 KB** |
| **Neutron (app route)** | **~3 KB** (Preact runtime) |
| Astro (with React island) | ~46 KB |
| Remix | ~58 KB |
| Next.js App Router | ~91 KB |

Static routes ship nothing. This isn't a compression trick — there is genuinely no JavaScript. The page is HTML.

App routes ship the 3KB Preact runtime plus component code. Preact is intentionally small: 3KB minified+gzipped vs React's ~45KB.

The implication: for content-heavy sites (docs, blogs, marketing), Neutron static routes reduce Time to Interactive to near zero because there's no script to parse and execute. For dashboards and interactive features, Neutron app routes pay 3KB instead of 60-90KB.

## Scenario 6: Memory at Sustained Load

RSS memory usage after 5 minutes at 100 concurrent connections.

| Framework | Memory (RSS) |
|-----------|-------------|
| **Neutron** | **~52 MB** |
| Remix | ~88 MB |
| Next.js | ~156 MB |

Neutron's lower memory footprint is partly because it doesn't carry React in its runtime and partly because the Node adapter is lighter. At cloud pricing, this matters — you can fit more Neutron instances on the same hardware.

## Scenario 7: High Concurrency (500 connections)

Same SSR-with-data scenario at 500 concurrent connections.

| Framework | Req/s | Error Rate |
|-----------|-------|-----------|
| **Neutron (static)** | **12,800** | 0% |
| Neutron (app route) | 9,200 | 0% |
| Remix | 6,100 | 0% |
| Next.js | 4,900 | 0.2% |

At high concurrency, Next.js started dropping ~0.2% of requests. Remix and Neutron handled all requests cleanly. This reflects queue depth and connection handling differences in the frameworks' Node.js adapters.

## Scenario 8: Build Time

How long `npm run build` takes on a 50-route project.

| Framework | Build Time |
|-----------|-----------|
| **Neutron** | **~8s** |
| Remix | ~14s |
| Next.js | ~23s |

Next.js does more work at build time (static analysis, route optimization, edge runtime preparation). Neutron's build is lighter because the static/app route distinction is simpler than Next.js's complex rendering model.

## What the Numbers Actually Mean

**Neutron's static routes are genuinely faster**, and the gap is real — not a benchmark trick. Static routes do less work by design. If your page doesn't need client-side JavaScript, don't ship it.

**Neutron's app routes (Preact SSR) are faster than Next.js and Remix**, but the gap isn't dramatic. For most applications, the difference between 9,800 and 14,100 req/s doesn't matter — your database will be the bottleneck, not your framework.

**The bundle size numbers matter more than the throughput numbers** for most user-facing applications. A 91KB JavaScript bundle takes ~300ms to parse on a mid-range mobile device. A 3KB bundle takes ~10ms. A 0KB bundle takes 0ms. This is the real performance win.

## Where Next.js and Remix Win

Let's be honest about the tradeoffs.

**Ecosystem.** Next.js has thousands of examples, tutorials, and third-party integrations. If you need a specific library or pattern, there's probably a Next.js guide for it.

**Community.** Next.js and Remix have large, active communities. Neutron is early-stage. If you hit a weird bug at midnight, Stack Overflow won't have the answer.

**Production battle-testing.** Next.js runs major production applications. Neutron has not been battle-tested at that scale.

**Deployment.** Vercel for Next.js is a seamless experience that's hard to match. Neutron targets Vercel, Cloudflare, and Docker, but the tooling is less polished.

If you're building something that needs to go live soon and can't tolerate rough edges, use Next.js or Remix. They're excellent frameworks.

If you're building a new project and you're willing to work with an early-stage framework in exchange for the performance and bundle size wins — and you want Nucleus's multi-model database under the hood — Neutron is worth exploring.

cd neutron/ts/benchmarks
npm install
