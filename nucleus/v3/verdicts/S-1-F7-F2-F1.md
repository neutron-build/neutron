## R1: does CHAIN-BUILD-UNDER-P fail now?

Yes, paper-caught. The steps:
- §4.2's allocation is deterministic: the lowest free LPID, else `next_lpid++`.
- The variant's split splits the leaf but not `P`, so it allocates exactly one LPID.
- Every LPID below the split's is mapped, so the split takes that LPID, the last its
  MapLeaf covers. §6.4 and §5.6 pin that MapLeaf before the prune, and the split's
  new page then keeps it resident (§4.1).
- Nothing in the operation frees an LPID below it:
  - the old value is inline, so there is no chain free;
  - the prune frees no LPID (§10.3);
  - the fixture is single-threaded.
- So every LPID the chain takes is greater than the split's and lies on a later
  MapLeaf. Those MapLeafs are evicted, unpinned and map no dirty page, so §4.1 does
  not force them resident.
- Under the mutant, `P` is still exclusively latched (the split installed its
  separator) when the build reads the first of those MapLeafs. The hook fires.
  - If the mutant instead takes the §5.6 restart arm on the cold MapLeaf, the
    hook's "no restart follows a mutation" check fires.
- The correct build releases `P` first and reads in place under the leaf alone
  (§5.6, §6.7 "Building"), so it passes.
- The inline old value removes the earlier false credit: no free reads cold before
  the build.

**Satisfiability.**
- The rewrite takes a tag-6 provisional value to a tag-8 one. Tag 8 carries the same
  header plus `len u64, first LPID u64` (§7.3). So the new cell is larger than the
  old one when the old inline value is under 16 bytes, and a full leaf with less
  free room than that difference and nothing prunable does split.
- The split's other dirty pages (the leaf, `P`) must not map onto the chain's
  MapLeafs, or the split would load them. "Those MapLeafs are the only pages the
  variant reads cold after the split" states that requirement, and grep 14 pins it.

## R2: is the arithmetic right?

Yes, for every cell size:
- §3.2 fits at least 4 maximum-size cells on a page, so `C_max ≤ U/4`.
- Coupling keeps `P` only when the leaf is not safe (§6.2), meaning
  `used > U − C_max ≥ 3U/4`.
- Any one cell, including one with a maximum inline value, is at most `C_max`. So
  after one delete, `used > U/2 > U/4`.
- The cells these deletes remove are tag-8 cells (a key, a 21-byte provisional
  header and 16 bytes), far below `C_max`.

On a safe leaf coupling had already released `P`. Either way the delete holds only
the leaf, which is §6.5's third bullet and never packs. The sentence says "one
delete", and §6.5 makes a coupled pack optional ("may pack"), so even a batched
cleanup would break no invariant. Ruling: sound, no conflict with §6.5. -F3's
planned "(no caller in 2.0: ...)" parenthesis is still consistent with it.
