## O-1 recommendation (the owner decides; the card's own question is unfair lock queues)
**Option A: keep v7.8's unfair wake-all everywhere.**
- *Costs.*
  - A relation-lock request can wait without bound under continuous traffic. This hits ACCESS EXCLUSIVE (ALTER, DROP, TRUNCATE, REINDEX) and SHARE (CREATE INDEX) requests, since a new ACCESS SHARE or ROW EXCLUSIVE request is granted past them whenever any weak holder remains.
  - Migrations then hang, or fail repeatedly under `lock_timeout`. Only stopping traffic helps.
  - Hot rows wake every waiter on each release, and the others re-park.
  - It is a listed divergence (S-2a-2 lists it).
- *Benefits.*
  - It is the simplest design: no queue state, no grant order, and no soft edges, so every graph edge is a hard conflict and I-LIVE (c) stays exact.
  - It avoids PostgreSQL's well-known pile-up, where one waiting ACCESS EXCLUSIVE stalls every later statement on its table.

**Option B: PostgreSQL 17's queues.**
- *What PostgreSQL does.* A new request waits behind an earlier waiter it conflicts with (`waitMask`). A transaction that already holds a lock on the object goes ahead of conflicting waiters.
- *Costs.*
  - Per-object FIFO queues in B-2a's relation and advisory tables, charged to `lock_mem`.
  - Soft edges from a requester to earlier conflicting waiters in B-2b's graph. This must use the simple form, where any cycle gives 40P01 and queues are not rearranged; PostgreSQL's queue rearrangement in `DeadLockCheck` would sometimes resolve such a cycle silently. That difference is a listed residual.
  - A dequeue on timeout, cancel, poison or 40P01 must re-check the waiters behind it (a lost-grant mutant).
  - About two harness tests and three mutants.
  - PostgreSQL's pile-up returns, as parity. DDL users mitigate it with `lock_timeout`.

**Recommendation: B for relation and advisory locks, A for row locks.**
- PostgreSQL's own row locks let a request that conflicts with no current locker pass waiters. Its tuple lock orders only those who wait, so for rows the remaining difference is waiter order and herd cost, not starvation. Per-key queues would also fight escalated runs.
- DDL starvation is a failure that the driver and ORM matrix will exercise (Flyway, Alembic and Prisma migrations under live traffic), and users cannot work around it.
- B-2a and B-2b have not started, so the change costs least now.

The crisp question for the owner: "Table-level and advisory locks: PostgreSQL's fair queue (a DDL waits only for the holders present when it arrived, but later statements queue behind a waiting DDL), or v7.8's unfair wake-all (no pile-up, but a DDL can starve under continuous traffic)? Row locks stay wake-all either way."
