## Ruling on the implementer's ESCALATE (loose-object swap)
**Real.** Reproduced on git 2.47.3, in two variants:
- **Card side:** the card's root tree file holds the scaffold tree's bytes.
- **Base side:** the scaffold's tree file holds the card tree's bytes.

In both, `diff --name-only scaf...card` under git-env.sh prints nothing, and
both refusals return 0. `git fsck` exits 3.

**The suggested fix does not work.** `rev-list --objects --verify-objects`
exits 0 in both variants. It re-hashes only objects the walk did not parse, so
trees and commits are never checked. A range limited to `base..card` also
misses the base side.

**In threat model.** A worker has the same uid write access to the common
objects/ directory that it has to info/grafts or the commit-graph. The
consequences are bounded:
- `git push` of either variant is rejected ("missing necessary objects"), and
  CI's fresh-clone audit reads the true objects;
- so this is a local fail-open of the runner and merge-card;
- the gate's own checkout also checks out the lie.

**Out of scope for this card.** It is a new class: a storage-integrity failure,
not a cache or config switch. The fix belongs in the range consumers, which
this card's Limits exclude.

**Cost of the fix is small.** A Merkle check hashes each object as read via
`cat-file --batch`. It starts from the ref tips: the commits on the walk, then
every tree under both compared root trees. On HEAD that is 916 trees in 0.05 s,
and it caught both swaps. Because it hashes whatever git returns, it covers
.idx, midx and .rev offset swaps too.
