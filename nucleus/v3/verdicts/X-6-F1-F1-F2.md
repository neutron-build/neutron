## Findings: rework items
**R1. The Goal is not met on the real opencode: its shell commands are not in its group (blocking).** The card's named case, "a bash tool call that ran `(sleep 30; git commit …) &`", still survives. opencode 2.2.5's bundled JS spawns `Shell.create` commands with `detached:!0`, and its spawner defaults to `detached ?? !0`, so each command calls `setsid`. Measured with real opencode and the runner's flags (`run --standalone --format json --auto`), against a local mock LLM, as a group leader like `process_group=0`:

```
opencode (pid pgid sid): 1959431 1959431 1959424
tool shell (pid ppid pgid sid): 1960348 1959525 1960348 1960348
forge (pid ppid pgid sid stat): 1960361 1 1960348 1960348 S
opencode exited; killpg(opencode pid, SIGKILL) -> ESRCH (group empty)
forge after the kill: 1960361 1960348 1960348 S
FORGE LANDED after the group kill
```

So setsid is not the narrow residual that the card and docstring describe. It is what every worker shell command does. XBG's premise ("bash without job control keeps the subshell in opencode's group") holds only for the fake. The docstring's "its bash tool's git and cargo, and anything they backgrounded" is false, and so is the unchanged `Popen` comment. The same `setsid` means the kill paths (silence, timeout, SIGTERM) do not reach a running tool command either; I read that from the spawn, not from a separate run. X-6-F1-F1's Finding 2 made the same assumption.

Real containment does not fit this card's Limits and Do-not, so it goes to X-6-F1-F1-F2-F1. What the rework must do here: state in the docstring, the comment and the XBG row names that this kill reaches only same-group children, and that real tool shells escape it, naming the follow-up.

**R2. The `finally`'s kill is a stale-pgid kill, and the docstring understates it (fix in this card).** After a normal exit, the `else` branch reaps and kills, and the group is then empty. The `finally` calls `killpg` on the same pid after the whole acceptance run, up to 60 minutes per command, not "within milliseconds". Proof in a throwaway PID namespace: after the first `kill_child`, a new unrelated job took the pid as its pgid, and the second `kill_child` killed it (`returncode -9`). The old guard could not do this on a normal exit. On this host `pid_max` is 4194304, and the counter moved 383,681 during this gate's roughly 9 minutes, with the mutant suites running alongside. So a wrap needs about 100 minutes at that load, or one gate on a host with `pid_max` 32768. The victim must be a live same-uid group leader on exactly that pid, so the odds are low, but a wrong SIGKILL is the one thing the Do-not forbids.

Fix within the Limits: make `kill_child` idempotent per child. Mark the Popen before the first `killpg`, skip `killpg` when already marked, and always `wait()`. Step 3's unconditional `finally` call stays and covers the signal gap. Correct the docstring.

**Answer on the `else` branch's ordering:** sound. `poll()` reaps first and `killpg` follows at once. While any member lives the kernel keeps the pid reserved, so survivors cannot be missed, and reuse needs the group already empty plus a full wrap in microseconds. The poll-loop kills are safe too: an exited unpolled leader is a zombie that pins its pid.

**R3. PermissionError: leaving it uncaught in `kill_child` is right, but the stated result is false (fix in this card).** The comment says "main()'s finally still writes the end record". Measured with `killpg` raising after a normal exit: the `else` raises, and the `finally`'s own `kill_child` raises again, since the group is the same. The finally aborts before its ledger append. The ledger holds only the start record. `refs_moved` is also skipped, and no RUNLOG row or result line is written. The outcome stays fail-closed: the run crashes with rc 1, `pass` is never set, and an open range counts every later commit as a worker's. But it is not what the card promised, and the old guard did write the end on this path.

R2's mark fixes it for the `else` path, because the `finally` then skips `killpg`. Add a row: a raising `killpg` after a normal exit still leaves an end record. By kernel semantics EPERM can also come from a group whose only remaining members run as another uid (a backgrounded `sudo`), not just a reused pgid; I did not run that case. The comment should say so.
