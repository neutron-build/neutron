## REWORK items

**R1. §6.8 step 3's reason is false (S-STORE:387; Work 4; G12 pins it).** The sentence says the space an under-full directory leaf wastes "is bounded by the number of trees, and a later CreateTree refills it".
- Tree ids come from a monotonic counter and are never reused (`alloc()` returns `next++`, C-T6-rehost §6; §6.8 "Tree ids"), and the directory is keyed by `tree_id` big-endian. A new entry therefore lands at the right edge, and no CreateTree ever inserts into a leaf to its left.
- No directory leaf is ever freed: nothing packs the directory, the sweep does not visit it, and the last step leaves an empty leaf in place (§6.1 allows it). DROP, TRUNCATE and a table rewrite each retire tree ids, so waste grows with the trees ever created, not the trees that exist: roughly one page per few hundred retired trees, kept for the store's life.
- The decision not to pack in 2.0 can stand, since the cost is small. The stated reason cannot. Work 4 sends a reason of this kind to P. Fix: state the true bound and record it as a known cost with a revisit trigger, and re-anchor G12. The sentence is inside Limit 1.

**R2. §4.2's corrected sentence is still false for overflow chains (S-STORE:161; Work 8; G33 pins it).** It says readers reach pages "only through latched parents … or, for a tree's root, through the root table".
- §6.7 "Reading without the leaf latch" and §6.6 "Batches" have a reader follow a chain after releasing the leaf latch, under a registered `S`. A chain's pages are reached with no latched parent at all.
- Reuse of a chain's LPIDs is safe for a different reason: the registration keeps the version, and so its chain, alive (I-GC-READEQ). That is the reason this sentence must cover, because the sentence is the argument for immediate reuse.
- Roots are now correct. `dir_root` is not a tree's root and is not in the table, but it is never freed and only directory changers latch it, so it needs nothing.
- Fix: add the chain case with its reason, inside Work 8's clause, and re-anchor G33. §6.2's closing paragraph (S-STORE:302), which §4.2 relies on, overclaims the same way: see F1.

**R3. A walk step that meets an unmapped root has two contradictory outcomes (S-STORE:380, 391, 393; §14 step 6).** Work 7 now says a walk step names the root through Root names, accepting `dropping`.
- Root names step (2): "A pin on this path that finds the LPID unmapped is a retry from (1), never XX001 or poison."
- S-STORE:393: "At open, an unmapped root of a `dropping` entry is corruption like any other unmapped reference (XX001); §14 step 6 needs no other arm."
- On a corrupt image both apply to the boot walk's first step. The entry never changes, because the walk is its only remover and one walk runs per tree, so following step (2) spins forever instead of raising XX001. §14 step 7's amcheck is optional and cannot be relied on. A live reader on such an image loops the same way.
- The rule that resolves it is sound and is the twin of the header-mismatch rule already in step (2): an unmapped pin retries from (1), and the same result under an unchanged entry is XX001. DropTree's last step removes the entry before it frees the root, so an unmapped root under an unchanged entry can only be corruption. `t_root_name_reuse` case C still passes, because the entry is gone there, and ROOT-PIN-UNMAPPED-FATAL still fails it.
- This predates the card (draft 7.6), but Work 7 makes it explicit, and this is the last card of the series. The fix sits in Root names, outside Limit 1 and the Do-not, so P must widen them by one clause first. This gate does not edit the card.
