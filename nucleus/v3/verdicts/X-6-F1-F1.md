## Findings
1. **Ledger lifecycle: sound.** The SIGTERM handler is installed, then the start
   record is fsynced, then one `try/finally` covers every attempt, the quota and
   disk `sys.exit`s, the stray stop, exceptions, SIGINT and SIGTERM. The finally
   ignores SIGINT/SIGTERM, kills a live child's group, and appends the end
   (validated 40-hex, else `null`, which reads as open and fails closed). A
   signal landing between the start append and `try` leaves an open range, which
   also fails closed. K shows SIGTERM mid-attempt gives rc 143, a dead child
   group and a closed range.
2. **Process group.** `process_group=0` plus `killpg` reaches opencode's
   children (G-KILL-NOT-GROUP is caught by K). As a side effect, a terminal
   Ctrl-C now reaches only the runner, whose finally kills the child: correct.
   Gap: the finally (and a normally finished attempt) kills the group only when
   opencode itself is still alive, so a backgrounded grandchild of an opencode
   that exited normally survives past the end record (X-6-F1-F1-F2).
3. **Fail-closed on malformed data: correct for what it catches, partly
   untested, and not total.** An unparsable line, a missing key, a falsy start or
   a failing rev-list returns None, and the caller trusts nothing. Direct probe:
   a non-string `start`/`end` (`123`, `{}`) raises TypeError out of
   `worker_commits` and crashes the run (no pass, the end is still written: safe
   but not graceful), and `start: "--all"` reaches `git rev-list` as an option
   and empties the worker set, so a forged verdict is exempt. Both need a write
   to cards/logs/, which is the shell-capable adversary the docstring
   explicitly excludes, so this is not blocking. Neither fail-closed branch has
   a scenario: G-MALFORMED-TRUSTS and G-REVLIST-FAIL-TRUSTS survive
   (X-6-F1-F1-F1).
4. **--trust-existing.** It applies only with `--keep` and no ledger, so it can
   never override an existing ledger. It writes a closed empty range at HEAD
   tagged `trust-existing`, and prints the trusted HEAD. A failed `git log`
   counts as "has a verdict commit" (refuses). The trust model is "the operator
   inspected the branch up to this HEAD", recorded. Sound.
5. **Ranges are keyed on SHAs.** An operator rebase or amend between runs (the
   plan rebases overlapping card branches) gives a worker's forged verdict commit
   a new SHA that is in no range, so a later `--keep` run trusts it when it is
   still the last commit to touch the verdict file. Workers cannot rewrite
   history (X-6-F1-F3), so this is an operator path; it is recorded as
   X-6-F1-F1-F3.
6. **Beyond-literal changes accepted.** The per-attempt `killed` variable fixes
   a real leak (the old `failure.startswith(...)` check skipped no-output
   restarts in later attempts after any earlier kill). The final scope check
   sets `scope` but never `pass`. Scenario K covers what C and I cannot see.
7. **Operational.** After merge, `--keep` on any existing worktree whose branch
   carries a verdict commit refuses until `--trust-existing`. The orchestrator
   must be told.
