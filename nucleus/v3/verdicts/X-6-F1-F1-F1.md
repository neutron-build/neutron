## Findings
1. **The fix is correct.** Parse errors (OSError, ValueError including
   UnicodeDecodeError, RecursionError) give None. Every record must be a dict with a
   str `run`. A start must be a full lowercase 40-hex id, and an end must be one or
   null. The dropped `TypeError`/`KeyError` arms are now unreachable: the loop
   type-checks before it indexes, and every argv word given to subprocess is a str.
   The rev-list is `--end-of-options END ^START ^BASE --`. Probed on git 2.47: an
   honest open range still puts the forged commit in the worker set, and the
   `--all` injection is gone. `main()`'s writers (pre_head, the trust-existing pair,
   and the end) all emit records that pass the new checks.
2. **Rulings on the implementer's deviations.**
   (1) `flagged_raw` is accepted. `res` json-parses every ledger line, so it cannot
   read XMA. The helper makes flagged's three checks and also pins "repair nothing":
   the bad line is still first, followed by this run's start and end. Unlike `res`,
   it does not kill a leftover fake opencode. That is harmless here (the runner's
   finally kills the group), but note it.
   (2) Accepted. Under `--end-of-options`, `end:"--all"` is a bad revision, which
   gives None, so END-UNCHECKED is caught only by `end:123`. That exposes a real gap:
   END-STR-ONLY survives, because no end-side case is a well-typed non-OID string.
   Probe: with that mutant, `end:"base"` (a ref name) closes the range at base and
   the forged commit is trusted. See F1.
   (3) RecursionError is accepted (a 100000-deep line gives None), but it is
   untested (F1).
   (4) A record with a str run and neither `start` nor `end` is ignored. Probed, it
   **cannot widen trust**: it adds no range, so it acts exactly like the line being
   absent. A record carrying both keys is read as a start, and its end is never
   given to git. The docstring's "anything else means trust nothing" reads a little
   broader than this. It is cosmetic.
   (5) Confirmed: on d7fe425b a `[]` line was silently skipped, not a TypeError.
   NOT-DICT-UNCHECKED is not equivalent. With the dict check gone, `r.get` raises
   AttributeError, and the row catches it.
   (6) NO-END-OF-OPTIONS is equivalent for ledger values, as ruled above. It still
   matters for an option-shaped `--base`.
   (7) The `wc` helper shadows coreutils `wc` for the rest of the script. Nothing
   after line 1826 calls `wc` or sources `core-paths-lib.sh` (whose
   `base_core_entries` runs `wc -c`) in-process, so nothing breaks today. But
   `cm`/`cpm`/`dr_cm` run in subshells, which inherit functions, so any future row
   using them after this block would call the Python helper. That is a latent trap
   (F1).
3. **Well-formed does not mean genuine.** This is not a defect of this card. A
   well-formed start that is not an ancestor (a commit built on top of the forged
   one) empties the worker set, and so does a well-formed `end == start`. Either
   lets a ledger writer exempt a forged verdict. That is the shell-capable
   adversary the docstring excludes. This card's job is fail-closed parsing and no
   option injection, and it does that job.
4. **Merge with X-6-F1-F2-F3-F1.** `git merge-tree --write-tree cb1a3c27
   card/v3-X-6-F1-F2-F3-F1` (e5362e07) is clean, with tree 10163b24. The merged
   run_card.py parses, and its `worker_commits` is byte-identical to cb1a3c27's and
   behaves the same in the probe. That branch adds other rev-list calls that take
   `base` without `--end-of-options`. Those are its own card's concern.
