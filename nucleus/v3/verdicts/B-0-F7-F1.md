# Findings (REWORK)

1. **R2-1 (blocks F1b): `reproduce.sh b` refuses after a FAILED or VOID run A, which contradicts the card.**
   - reproduce.sh lines 227–236 add a refusal (exit 4, "the verdict is already INVALID — run 'verdict'") whenever run A has no JSON or is voided. Reproduced: a FAILED A, then `b`, gives exit 4.
   - Card Work 7 says `b` refuses only "if run A has not finished, or if run-b.json or a failed run-b.log exists". A failed run A *has* finished.
   - B-0-F7-F1b Work 3 is explicit: "Run B is executed even if run A was refused, because both runs are evidence for the P escalation." Run B's purpose here is the P escalation, not the J6 word. Whether a refusal is systematic (both runs wedge) or a one-off is exactly what P needs to judge.
   - The worker made this choice on purpose (comment at line 227), but it overrides the card text. As shipped, F1b would hit the refusal, and its own rule ("if reproduce.sh misbehaves, stop and ESCALATE") would leave the escalation without run B's evidence.
   - Fix:
     - delete that early refusal;
     - keep the existing refusals;
     - `verdict` already derives INVALID from run A first, so its word is unchanged;
     - flip selftest S2 and S3 to expect `b` to run, and then check that `verdict` still names run A.
2. **R2-2 (regression from the R3 fix): `driver.sh` now hides every search-pass failure reason behind the settle transcript.**
   - `settle_pass` now tees the whole settle transcript to stderr, including a successful one.
   - `failure_message_tail` prefers stderr whenever it is non-empty. So when the *search* fails after a good settle, the FAILED line shows the settle polls ending "index state: settled …" and not the reason. Before the rework, stderr was empty and the line fell back to the NB_LOG tail, which held the refusal.
   - A J1 sanity refusal of a warmup or run pass is one such failure, and F1b expects that outcome to be recorded and escalated.
   - Reproduced by running the reworked driver.sh in `run` mode with a stub NB_BIN, where the settle succeeds and the search exits 1 with "latency sanity … > 10 ms". The driver's stderr is the settle transcript only; the refusal is only in NB_LOG. The b66814ff driver gives empty stderr, so its line falls back to the NB_LOG tail, which holds the refusal.
   - `copy_evidence` does not copy the pass logs (`<series>-<mode>-<n>.log`) or their metrics, so the reason is not in `repro/` either.
   - Fix:
     - put the settle transcript on stderr only when the settle fails, for example `… > settle.log 2>&1 || { cat settle.log >&2; exit 1; }` while still teeing to stdout as before;
     - and/or copy the pass logs into `repro/run-<x>/` as well.
   - Add a driver-level stub test for both cases: a J4 mismatch reaches the FAILED message, and a search refusal reaches it.
3. **R2-3 (minor): the selftest's mktemp defaults to `${TMPDIR:-/tmp/opencode}`.** That is the worker sandbox's directory. On a host without it, and with TMPDIR unset, the selftest dies at `mktemp`. Use `${TMPDIR:-/tmp}`.

Notes (no action required):
- A non-zero `nbench run` with neither a FAILED line nor a `results:` line (a harness or podman error before the row starts) is classed as "did not happen". Its evidence is copied, and the next `a` treats it as the killed attempt. That is consistent with F1b's rule. But `repro/run-a/` then mixes both attempts' files, which F1b's RESULT should note if it ever happens.
- Run A's `REPRO` date is taken before the quiet wait (up to 30 min). The script already documents "run the protocol inside one UTC day". F1b's operator should not start `a` after about 23:00 UTC.
