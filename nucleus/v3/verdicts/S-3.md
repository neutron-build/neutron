## The author's addition, STALE-FENCE (§9.1 step 4.4): accepted
- **The race is real.** T2 releases ShareUpdateExclusive at release (C-T0 §3.3 step 4), and T3 is a separate txn. A TRUNCATE queued for AccessExclusive can be granted between the two and commit at `D > f`. Its catalog writes are invisible at `f`, so a load that resolves trees at `S = f` uses the pre-TRUNCATE relation tree. Loaded into the current index tree, that publishes entries for rows the TRUNCATE removed.
- **The check closes it.** T3 reads the latest catalog under its lock. A TRUNCATE's lock is released only once `visible_ts ≥ D`, so the latest read sees that TRUNCATE. Unequal tree ids make the build restart at step 3, with a fresh `R` and fence, and the TRUNCATE kept WriteOnly. Equal ids mean no tree-replacing DDL committed in `(f, lock]`. No such DDL can commit afterwards before step 8, because T3 holds the lock. DROP TABLE and DROP INDEX in the window give 55000 at step 4.3. The future S-3a rewrite is covered because the comparison is generic.
- **The test catches it.** `t_build_truncate_before_load` asserts both the restart and that the published index matches the post-TRUNCATE rows. Under the mutant, the "old relation tree into the current index tree" form fails I-IDX, and every form fails the restart assertion.
  - A non-harmful variant loads the old relation tree into the old, retired index tree. That variant is caught only by the restart assertion. B-4d should make the restart observable, for example by counting fence commits.
