## Findings

1. **E-IO: StdEnv `read_at` still fails just below `i64::MAX` (minor).**
   - The guard is `off > i64::MAX`. Linux `pread` returns EINVAL whenever `off + count` overflows `loff_t`.
   - Probe with a 4-byte buffer on a 3-byte file:
     - `read_at(i64::MAX - 1)` is STD `Io{InvalidInput}`, MEM `Ok(0)`;
     - `read_at(i64::MAX)` is STD `Io{InvalidInput}`, MEM `Ok(0)`;
     - `read_at(i64::MAX - 4)` is `Ok(0)` on both.
   - The card's new E-IO clause ("any offset at or past end-of-file returns 0") is broken in that window, and the suite tests only `1<<63` and `u64::MAX`.
   - No real store offset comes near it, so this is not blocking. A-1b-0-F1.
2. **Huge `write_at` / `set_len` (the author's open point (a)).**
   - MemEnv `write_at(1<<63, b"x")` *panics* (`capacity overflow`) while holding the state mutex.
   - That poisons the whole MemEnv family: afterwards every call, `exists` included, is `Io{Other, "internal mutex poisoned"}`.
   - At a large offset that still fits memory accounting, such as 1<<40, the zero-filled resize would OOM-abort instead.
   - StdEnv returns `Io{InvalidInput}` for both calls at 1<<63.
   - E4's `SimDisk::write_at` (`off + len`, then `resize(end as usize)`) has the same shape, and A-1b copies it unchanged.
   - **Ruling: not blocking.** MemEnv is a test backend, no store path computes such offsets, and nothing consumes the trait yet. It still needs a rule before SimEnv runs fuzzed or faulted offsets. A-1b-0-F2, folded into A-1b, not into a later MemEnv card.
3. **E-LOCK same-handle re-lock and conversion diverge (pre-existing from A-1a, outside F1–F3; found by probe; matters for A-1b's API).**
   - On one handle:

     | Sequence | MemEnv | StdEnv (flock) |
     |---|---|---|
     | `lock_shared` then `lock_exclusive` | `Locked` | `Ok` |
     | `lock_exclusive` twice | `Locked` | `Ok` |
     | `lock_exclusive` then `lock_shared` | `Locked` | `Ok` (converts) |

   - The trait text ("succeeds only if no *other* handle holds any lock") matches StdEnv, not MemEnv.
   - Worse, StdEnv on Linux: when a handle holding a shared lock tries `lock_exclusive` and another reader holds shared, the call is `Locked` *and the handle's own shared lock is silently dropped*. Flock conversion is not atomic. After the other reader unlocks, a third handle's `lock_exclusive` succeeds.
   - §14.1's reader and writer locks rely on E-LOCK, so this needs one rule before SimEnv copies either side. A-1b-0-F3.
4. **Suite gaps that my own mutants found (minor).**
   - O1: `unlock` resolving by open-time name and silently returning `Ok` once the name is gone is UNCAUGHT. No check unlocks after a rename, although E-LOCK's new sentence says `unlock` releases "whatever name the file has by then".
   - O5: an `IsADirectory` refusal naming the wrong path (`to` for `from`) is UNCAUGHT. The card-specified `io_kind_is` checks no path, while E-KIND says each refusal's `path` names the path it is about.

## Follow-ups

A-1b's Limit 4 forbids edits to `env.rs`, `mem.rs`, `std_env.rs` and `tests/common/`. Folding F1–F4 into A-1b therefore needs its author to widen Limit 4 to exactly these items. The alternative is one small card, run just before A-1b; that is the orchestrator's call under the fold rule. Either way, F2's and F3's rules must be in the trait before SimEnv implements it.

- **A-1b-0-F1 (fold into A-1b): StdEnv `read_at` near `i64::MAX`.** Read only `min(buf.len(), i64::MAX - off)` bytes, with `Ok(0)` when `off >= i64::MAX`, so `off + count` never overflows `loff_t`. Extend `io_edges` with `read_at(i64::MAX)` and `read_at(i64::MAX - 1)` on a 4-byte buffer, each `Ok(0)`. The must-fail mutant is today's `off > i64::MAX` guard.
- **A-1b-0-F2 (fold into A-1b): bound `write_at`/`set_len` offsets.**
  - Add an E-IO clause: a `write_at` whose `off + len`, or a `set_len` whose `len`, exceeds `i64::MAX` is `Io { kind: InvalidInput }` on every backend, which is StdEnv's behaviour today.
  - MemEnv checks this before taking its mutex and before any resize. SimEnv checks it before calling `SimDisk::write_at`/`set_len`, the same way as the zero-length-write exception, so `disk.rs` stays as copied.
  - In MemEnv and SimEnv, grow with `try_reserve` and map an allocation failure to `Io { kind: OutOfMemory }`, so the backend never panics with the lock held. Optionally add a documented in-memory length cap.
  - Add `io_edges` cases at `1<<63` for both calls, and a check that the env still works afterwards (no poisoning).
- **A-1b-0-F3 (fold into A-1b): E-LOCK on a handle that already holds a lock.**
  - Pin one rule and state it in E-LOCK. Recommended: re-taking the mode a handle already holds is `Ok`; a conversion (shared to exclusive or back) is `Locked` on every backend and keeps the lock the handle already holds.
  - StdFile records the mode it holds (an atomic in `StdFile`; no libc) so it never asks flock to convert, which on Linux can drop the held lock on failure.
  - MemEnv and SimEnv follow the same rule.
  - Add a shared check for all three sequences, plus "a failed upgrade keeps the shared lock".
- **A-1b-0-F4 (fold into A-1b): conformance gaps.**
  - In `lock_moves_with_rename_until_drop`, or a sibling check, add: lock, rename, `unlock` through the old handle, then a new handle on the new name takes `lock_exclusive`. O1 must then fail.
  - Give `io_kind_is` a `want_path` and use it at every call site, so O5 must fail.
  - Record O3 in the check's doc as caught only on platforms whose errno differs (macOS).
- **A-1b-0-F5 (fold into D-5a; note for the A-6/A-7 authors): OpfsEnv and E-HANDLE.**
  - D-5a first verifies whether an OPFS file with an open sync access handle can be moved or removed.
  - If it cannot, D-5a either builds an id indirection (backing entries named by file id, plus a durable name table that `rename`/`remove` update) or names a departure in its own card.
  - Meanwhile the store should rely on a handle surviving a rename only where E4's `wal_recycle` does, and never on a handle surviving a `remove`, so that any OPFS departure stays narrow.
