## Findings (REWORK)
R1. **Bypass: the clean-filter refusal skips drivers literally named `set`, `unset` or
`unspecified`, in both twins.**
- *Where:* git-env.sh `case $val in unspecified | unset | set) continue`; run_card.py
  `if val not in ("unspecified", "unset", "set")`.
- *Why it matters:* `git check-attr` prints the same word for the state and for a string value of
  that name. git, however, treats `filter=set` as a driver named "set" and runs
  `filter.set.clean`.
- *Reproduced on git 2.47.3:*
  1. Commit `orig`, then `sleep 1.2`, then a same-size edit to `EDIT`.
  2. Write `f filter=set` to `.git/info/attributes`.
  3. `GIT_CONFIG_PARAMETERS="'filter.set.clean'='echo orig'"`.
  4. Result: `git status --porcelain` is empty, and `git_state_refuse --index` exits 0. The same
     happens for `unset` and `unspecified`. The `h` control is refused.
  5. Python's `git_state_problems` returns `[]` for `filter=set` with `filter.set.clean` in repo
     config (control `h`: named).
- *Fix:* skip no value. Look up `filter.<value>.clean/.process` for every distinct value. Checking
  `filter.set.clean` for a bare `filter` attribute costs one config read and cannot be a false
  positive in normal use.
- *Tests:* add rows for `filter=set` (and one of unset/unspecified) in both twins, plus a mutant
  that restores the skip.

  - Pointing core.excludesFile at a nested tracked .gitignore re-anchors its patterns at the top,
    and check-ignore then names that .gitignore as the source (probed with `a/.gitignore`,
    `./a/.gitignore` and an absolute path). The "at or above" check limits what is dropped to paths
    below that file's own directory D. So the trick gains something only for a pattern that begins
    with D's own path.
  - None of the 22 nested tracked .gitignore files has such a pattern (checked).
  - A worker who can commit a .gitignore in D could already commit `*` there.
  - **A worker committing a .gitignore in its own card:**
    - it is a listed diff path, judged by scope and visible to the gate;
    - it hides only untracked files below its own directory;
    - those files are never committed, so they never merge. Their only effect is on runs that read

## ESCALATE ruling: index-stat poisoning
The ESCALATE is real. I reproduced it:
1. Write `f filter=h`, edit f, `sleep 1.2`, run one status under `-c filter.h.clean='echo orig'`,
   then remove the attribute.
2. Under git-env.sh, `status --porcelain -uall --ignored=matching --ignore-submodules=none` and
   `diff` are both empty, and `git_state_refuse --index` exits 0, while f holds `EDIT`.
3. A filter-free `hash-object --no-filters` against the `ls-files -s` blob flags f.

The index stat cache is git's own state: no config key, flag or listing reaches it, and writing the
index directly does the same. It is **not in this card's scope**. It also is **not folded into
X-6-F1-F2-F3-F1**:
- That card re-hashes commits and trees for the range consumers. That is committed data, and it does
  not hash blobs.
- This is worktree-versus-index, for uncommitted data, read by other consumers.
- That card's Do-not forbids touching `git_state_refuse`/`git_state_problems`.

The two are complementary: the content check below also catches a swapped *blob* in a checkout,
which X-6-F1-F2-F3-F1 does not cover. The fix is a new card, **X-6-F1-F2-F2-F1-F1** (described
below), which depends on X-6-F1-F2-F3-F1 so that it can reuse `verify_objects`.

**Exposure.**
- The runner never commits or merges.
- Scope reads committed trees plus status.
- Hidden uncommitted content therefore never merges.

What it can fake is a green run on content that is not committed. That covers:
- the runner's acceptance run, which is advisory;
- a gate run in the worker's worktree;
- promote-pass's gate in the pass worktree. A same-uid worker that can write the common dir can
  poison that worktree's index too.

**Fresh checkout instead of a content check? Both are needed, and neither is enough alone.**
- A fresh detached checkout gets a new index and no untracked files, so it removes the worker's
  index entirely. It is the primary control.
- But `git worktree add` is not automatically honest. Probed on git 2.47.3:
  - a `post-checkout` hook in the common dir runs during `worktree add`. It could rewrite files and
    re-poison the new index;
  - a smudge filter from repo config plus `info/attributes` rewrites a file at checkout. Status
    caught it here only because the checkout was racy.
- So the permanent rule is: a fresh checkout made with hooks off, then verified by content before
  `gate.sh` runs.
