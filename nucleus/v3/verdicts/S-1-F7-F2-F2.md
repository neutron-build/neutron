## Findings

**R1 (blocking): the writer-intent bit adds a wait to latch holders, and with positioned cursors that is a deadlock.** §6.6 says a positioned cursor holds shared latches on its whole root-to-leaf stack, so it always holds its tree's root. The new rule makes a new shared `try_latch` fail while the bit is set, and the reader re-descends indefinitely. Two cycles follow; neither exists at the scaffold, where a shared `try_latch` beside a shared holder always succeeds:
- *Same tree.* Thread T holds cursor C on X (its root is shared). A writer W to X fails and sets the bit. T then reads X (a nested lookup during the scan, or a second cursor on X, as in a self-join). T's root `try_latch` fails while the bit is set. W never gets the latch, because C holds it, so W keeps the bit set. C is released only when T proceeds, and T never does.
- *Across trees.* T1 holds a cursor on X and reads Y. T2 holds a cursor on Y and reads X. Writers W_X and W_Y each set their bit, behind T1's and T2's cursors respectively. T1 spins on Y's bit and T2 on X's. That is a cycle. So an exemption only for "a thread already holding this root" is not enough.

This also breaks §5.3's "a frame's latch is never held across a wait on another transaction": T holds its cursor's latches while it waits on W's bit. The card prescribed the mechanism (Work 3), and the worker implemented it faithfully, so this is a card defect. It is fixable within Limits 3–4, which is why the verdict is REWORK, not ESCALATE.

Fix: the bit fails a new shared `try_latch` only for a thread that holds no frame latch other than the directory leaf it is descending through. A thread holding latches, such as a positioned cursor's, ignores the bit, just as §5.6 lets a latch holder skip a blocking gate acquire. A thread the bit can stop holds nothing once it backs off, so it cannot close a cycle. The steady-reader starvation variant still holds, because its readers hold nothing.

Also state the cost the card's cursor sentence leaves implicit: while a writer waits behind a positioned cursor on X, new latch-free readers of X are held off for the cursor's life too, not only the writer.

Add a `t_dir_root_no_stall` cursor variant with both cycles above: every read finishes within the budget, and X's writer finishes once the cursors release. Add the mutant ROOT-INTENT-BLOCKS-HOLDER (the bit also fails a thread that holds latches), which fails that variant. This needs a card amendment (Work 3–4, the mutation table, the Acceptance greps and the I-LATCH mutant column).

**R2 (blocking, small): the new MapLeaf's creation is not conditional.** Two allocations can restart on the same missing MapLeaf. The text says each "creates and pins its empty MapLeaf". A second, unconditional creation replaces the MapInner ref after the first allocation's retry may already have mapped an LPID into the first MapLeaf, so that mapping is lost, which breaks I-LPID-EXACT. The rule must say that the gated operation creates it only if the ref is still null, checked under the MapInner's exclusive latch, and otherwise pins the existing one. It must also say that the frame is obtained (which may evict) before that latch is taken: a dirty eviction of a MapLeaf updates its parent ref (§4.1), and §5.3 forbids I/O under an inner exclusive latch. The sentence "creating a page may evict … so it never runs under an inner exclusive latch" says this only for `P`, not for the MapInner the creation itself latches. This fits within Limit 2.

**R3 (small): it is not said which frame's bit is cleared.** "The writer clears the bit when it takes the latch" assumes that the root it re-finds is the frame it set the bit on. If another writer splits or collapses the root meanwhile, or DropTree frees it and §4.2 reuses the LPID, the bit stays set on a frame that is no longer X's root. That frame also stays pinned for as long as the bit is set, which leaks a pin against §5.4's minimum. State that the writer clears the bit on, and unpins, the frame it set it on when it takes any root latch for the operation or abandons it. This fits within Limit 3.

## Rulings on the worker's judgment calls

1. **"In a gated operation of its own, with no other latch held."** This is a faithful reading, not a scope change. Creating a MapLeaf mutates its MapInner through `write_guard` (§4.1). Outside the gate, a flip could cut that mutation without the epoch copy, so the card's "with no latch held" cannot mean "with no gate". R2 is a gap in how the step is stated, not in this choice.
2. **Liveness.** Sound, as lock-freedom, not wait-freedom.
   - *The pin bound.* Each held pin keeps at least one free LPID, so before a restart the pins number fewer than the free LPIDs under them, which number fewer than `n`. One more pin gives at most `n`.
   - *The restart bound.* With no concurrent allocation or path change, frees only add LPIDs and the retry prefers pins, so the bound of one holds.
   - *Further restarts.* Each is charged to an operation that took LPIDs, a mutation after which that operation never restarts, or that changed the path. So the system progresses.
   - *The §4.2 exception.* It harms none of the fixtures that rely on lowest-first. S-1-F7-F2-F1's CHAIN-BUILD-UNDER-P build variant allocates the chain after the split's mutation, which is not a restarted retry, and the split takes the last LPID of its MapLeaf, so any pin it held is dropped. In `t_split_reserve_order` and `t_drop_every_cut`, the retry on the pinned MapLeaf takes the same LPID that lowest-first would.
   - *Note (pre-existing, not this card's).* "Within §5.4's `R_MAP`" is loose. `R_MAP` is sized `⌈dirty frames / 510⌉` for the pins of MapLeafs that map dirty pages. The pins an allocation takes before it maps anything, here and in draft 7.3, are not in §5.4's formula. The card dictated the phrase.
3. **The intent bit.** It cannot leak across a crash: it is in memory and never persisted. In process it can leak only through R3. Latch-free readers are delayed at most until the current holders drain plus one writer operation, except behind a positioned cursor (R1's cost note). The bit does starve readers that hold latches, which is R1. A steady stream of writers can still starve readers, a trade-off the card accepts implicitly.
4. **§15 additions.** Accepted; each one makes a mutant reachable:
   - the cursor staying past the budget in the flip variant (without it, ROOT-RETRY-HOLDS-GATE could pass once the writer succeeds);
   - overlapping readers in the starvation variant (the card's own check);
   - the fixture evicting the lowest free LPID's MapLeaf (FREESET-LOCK-IO's cold path);
   - the hook's page-table clause (FREESET-LOCK-INVERT becomes deterministic).

   "No … frame latch while the lock is held" must mean "taken": the allocation holds `P`'s latch when it takes the lock. Reword this in the rework.
5. **§6.8's mutant list.** Leaving ROOT-RETRY-HOLDS-GATE and ROOT-WRITER-STARVES out was correct under Limit 3. The I-LATCH column is authoritative. The rework's card amendment may widen Limit 3 to add both, plus ROOT-INTENT-BLOCKS-HOLDER, to §6.8's list.
