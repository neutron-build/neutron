## Findings

**E1 (escalated, blocking): anomaly (b) is a real lock-order hole, and resolving it is a cross-spec decision.**

What the specs already say:
- §5.3: "Latches are acquired top-down, and among siblings left to right (I-LATCH, §6.2). Nothing ever latches sideways or upward, so latching cannot deadlock."
- §6.2 orders latches by (depth ascending, then left to right).
- §6.8 says "For I-LATCH, the directory leaf is the root's parent". That makes the directory plus every tree a single order with `dir_root` at the top.
- C-T0 §2.6 level 4 takes page latches "in S-STORE §5.3's order", and "a thread holding a lock acquires only locks further down the list".

A positioned cursor holds its tree's root-to-leaf stack (§6.6). A nested read by the same thread starts at `dir_root`, above every latch the thread holds, so it latches upward. Both S-STORE and C-T0 forbid that.

What the reworked §6.8 says instead:
- that the shape proceeds: "a cursor holder that reads its own tree ... takes the root shared and proceeds, and two cursor holders that each read the other's tree ... both proceed";
- that its exemption covers "a thread that holds any other frame latch".

The cursor variant of `t_dir_root_no_stall` requires A-7b to build the shape. So the card now contradicts I-LATCH and C-T0 §2.6. The cycle argument it gives ("a thread the bit stops holds no latch") covers only the bit's own waits, not the latch waits of the exempt threads.

Deadlock freedom, shape by shape:
1. **A latch-free reader that the bit stops.** Safe. Once it backs off, it holds no latch and no gate. Its pins and its directory-leaf hold are released, so nothing waits on it.
2. **A positioned-cursor holder doing a nested shared read, same tree or another.** Safe at the latch level, but only by an argument the spec does not state. A cursor's stack is shared and closed under ancestors. A thread that wants a page in that stack exclusively couples down to it top-down, so it would already hold the page's parent exclusively. That parent is in the stack and held shared, so this is impossible except at the root. The root is taken only with `try_latch`, by writers (§6.8) and by DropTree, and so are eviction victims and epoch copies (§5.2, §5.6). No thread ever blocks on a positioned cursor's latch, so a cursor holder can wait but can never be waited on, and it cannot lie on a latch cycle.

   It is not safe at the pool floor. §5.4's per-thread quota is `height + 2`, one path. A nested reader holds its cursor's path plus the nested descent. With enough nested threads every frame can be pinned, and every thread then waits for an unpin while it holds pins. "The minimum makes that wait finite" is then false. Legalizing the shape needs a bounded nesting depth and a §5.4 term for it.
3. **A nested reader whose hold is not cursor-shaped**, such as a leaf held without its ancestors, or any exclusive latch. **Refuted.** T1 holds X's leaf `L` exclusively and reads Y down to Y's leaf `L'`. T2 holds `L'` exclusively and reads X down to `L`. Each passes the other tree's root shared, with no bit involved, and each blocks on the other's leaf. The exemption's class ("any other frame latch") admits both threads, so §6.8's "proceeds" is false for the class it names. At most it holds for shared, cursor-shaped holds.
4. **A thread inside a gated operation.** Safe. It meets a root only before its first mutation (§6.8 "an operation latches its root before its first mutation"). A failed `try_latch` releases the directory leaf and the gate; what remains are its lock-table entries (C-T0 level 1) and pins. No reader waits on those, so no latch cycle forms.

   A writer that holds a positioned cursor is excluded by C-T0 §2.6: lock-table entries precede every latch. If such a writer were allowed, it would livelock on its own tree, because its own cursor holds the root shared. Its bit would then stop every latch-free reader of that tree for good. The livelock exists without the bit; the bit spreads it to every latch-free reader. Whichever way E1 is ruled, §6.8 should say that only a writer holding no frame latch sets the bit.
5. **A thread holding MapLeaf pins** (an allocation restart's pins, or the bit's root pin). No latch edge, since pins are not latches. Such a thread enters only §5.4's frame wait, which is anomaly (d) below.
6. **Nested reads in general.** Safe only under shape 2's conditions: shared, cursor-shaped holds, bounded depth, and counted in §5.4. Unsafe otherwise (shape 3).

The starvation guarantee that survives:
- **Guaranteed.** A writer whose bit is set gets the root once the shared holders present when the bit was set have released, plus one bounded backoff. This holds provided no exempt (latch-holding) thread holds or re-takes the root, and no other writer wins it first. A stream of latch-free readers alone cannot starve it.
- **Not guaranteed.** Positioned cursors, for their life, which nothing bounds until A-4e does. Streams of latch-holding readers, without bound. Other writers: there is no FIFO among writers, and another writer's abandon clears the shared flag (see (c)).
- **The converse cost.** Latch-free readers of the tree are held off for as long as the writer waits. That is without bound behind a cursor, and also behind a stream of latch holders, which §6.8 does not say.

Why this is ESCALATE and not REWORK: the fix is a choice between two designs.
- **(A) Legalize cursor-shaped nested reads.** Add an explicit exception to §5.3/§6.2's order and I-LATCH's statement, with shape 2's argument. Narrow the exemption to shared, root-to-leaf cursor stacks. Bound the nesting depth and count it in §5.4. Edit C-T0 §2.6 level 4. This card's Limits exclude all of that, and its "Do not" list excludes C-T0.
- **(B) Keep the order as written.** A thread that holds page latches never descends the directory; a cursor releases first (§6.6). This is within Limits 3–4. §6.8 then says that every thread that meets the bit holds at most the directory leaf, so the bit cannot close a cycle. The exemption stays as a defensive rule, the "proceeds" sentences go, and the cursor variant is recast as a robustness check or dropped. 9970d714's R1 cycles then cannot arise legally.

(B) constrains the executor (index scan with table lookups, nested-loop joins, open portals while the same session reads) and A-4e's release policy. That is an owner or P design decision spanning S-STORE, C-T0 and the row layer, not a text fix. My recommendation: (B) in this card, because it matches both specs as they stand. Then raise (A) as its own card if A-4e or the executor needs held cursors.

**R4 (blocking under either ruling, within Limit 4): the moved-root variant cannot reach ROOT-INTENT-WRONG-FRAME, and its hook fails the correct rule.**
- *The mutant is unreachable.* Under I-ROOT-STABLE (§6.3), a root split or collapse rewrites the root page in place. The waiting writer's pin keeps that page in the same frame, so "the root it re-finds" is the frame it set the bit on, and the mutant behaves exactly like the rule. The frames differ only when DropTree frees the root (§4.2 may then reuse its LPID) and the writer's fresh descent finds the entry absent, so it abandons. Under the mutant, nothing is re-found and the bit stays on the old frame. If the reused LPID's page lands in that frame, a new tree's latch-free readers are stopped indefinitely.
- *The hook is wrong.* "At each operation's end ... no frame's writer-intent bit is set" also fires when the splitting writer ends while the first writer is still backing off with its bit legitimately set.
- *Fix.* Build the variant on DropTree plus a CreateTree that reuses the LPID, and on the abandon path. Scope the hook to the end of the first writer's operation. §6.8's "if another writer splits or collapses the root meanwhile" is vacuous under I-ROOT-STABLE and can go; 9970d714's R3 made the same slip.

**Sound, as checked.**
- *R2.* The creator under the MapInner's latch waits on nothing but the page table. A MapLeaf evictor that latches the MapInner (§4.1) therefore cannot cycle with it. The "pin, releasing the latch first if it must load" path re-reads by radix position, which is stable.
- *R3's clearing rule* is correct apart from R4's test.
- *ROOT-INTENT-BLOCKS-HOLDER* is caught on paper, if E1 keeps its shape legal.

## Rulings on the implementer's anomalies

- **(a) MapInner and level growth: follow-up, not blocking.** Map growth is unspecified at the scaffold too: §4.1 never says how a MapInner or a new level is made. MapInner pages live outside the pool (§5.7), so creating one evicts nothing, and R2's frame-before-latch concern does not arise for them. R2's lost-mapping race does recur, though, for two restarts that create the same MapInner, or a new `map_root` level. See S-1-F7-F2-F2-F1.
- **(b) Blocking: E1.**
- **(c) One shared flag: fine as specified.** Clearing on take is harmless. The taker holds the root exclusively, and every other waiting writer sets the bit again on its next failure. Clearing on abandon reopens the root to latch-free readers until another waiting writer's next failure, one backoff, so only a stream of abandoning writers could starve a waiter. Pins are per writer and unaffected. Worth one sentence in §6.8 (S-1-F7-F2-F2-F3); a count would close the abandon window.
- **(d) The waiting writer's root pin: fine on its own, follow-up for §5.4.** The pin is on the frame the writer will latch next as its root, so it lies inside the thread's own path quota. During the directory descent the thread holds at most two coupled directory pages plus that pin, which is at most `height + 2`. It can coexist, though, with up to `n` allocation-restart pins, which §5.4's formula does not count (9970d714 judgment call 2's note, pre-existing since draft 7.3). See S-1-F7-F2-F2-F2.
