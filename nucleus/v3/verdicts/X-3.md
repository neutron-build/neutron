### REWORK items (blocking)

1. **Concurrent `gc()` loses committed writes.** Every gc call takes row
   locks under the same identity `GC_TXN = 0`. Re-acquire by the same
   owner is a no-op, so one gc's `release_all(0)` frees a key that
   another gc is still deleting under. A writer then acquires that key
   and commits a live value. The other gc, which re-read the old
   tombstone, deletes that value.
   - I reproduced this with 4 writer threads doing delete, put and
     read-back on their own keys while two threads looped `gc()`. A
     committed put stayed `None` for 100 ms with no other writer: 3 of 9
     runs. One gc thread: 0 of 9. No gc: 0 of 9.
   - `TxnEngine::gc(&self)` does not forbid concurrent callers.
   - Fix inside the crate: serialize `gc()` with an engine mutex, or
     take a fresh TxnId from `next_txn` per gc call.
2. **The GC lock and re-check have no test.** Removing the key-lock
   acquire from the tombstone delete (GC-NO-LOCK) passes every test in
   the crate. The delete then races writers and loses their values
   (caught 3/3 by the gate's probe). Add a concurrent GC-vs-writer test
   to `tests/` that catches both GC-NO-LOCK and the concurrent-gc case.
   Shape: writers delete, put and read back their own keys while one or
   two threads loop `gc()`. Retry each read-back until the
   commit-visibility window closes.

### Non-blocking notes (fix with the rework if cheap)

- S13 runs only with the 64 MiB budget, so it never exercises spilled
  records under its mid-schedule `gc()`. An over-trim of the spill index
  alone is caught only by S12 in the low-budget run. Adding an S13 run
  with `undo_budget_bytes = 4096` costs one `#[test]`.
- `stats()` walks chains at an unregistered `visible_ts`. A concurrent
  `gc()` can trim a record that walk needs, and the error is silently
  dropped from `logical_bytes`. The count is understated, and nothing
  is reported. Register a snapshot for the pass.
