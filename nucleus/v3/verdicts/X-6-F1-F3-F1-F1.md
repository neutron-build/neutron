## Findings
- **RF11: correct.** `git fetch -q . +card/v3-RF:card/v3-ZZ` force-moves the
  template's existing `card/v3-ZZ` (at the base tip) onto the worker commit.
  The `rf` helper requires the named set to be exactly `{refs/heads/card/v3-ZZ}`,
  so both a miss and an extra entry fail. The ref is unprotected, so only R1 can
  name it, and that is why G-R1-CREATED-ONLY is caught here alone.
- **e2e RF1 restore line: correct, with real ids.** `restore_main` requires the
  exact line (two-space indent, full 40-hex `main_old`, then `H`, the card tip
  that main was fetched to). `main_old` is read after the run from
  nucleus/v3-scaffold. That equals main's snapshot value only because main is
  reset there before XR1 and XR3, the one scenario that moves the scaffold,
  stays last. The existing "RF3 (control, last)" comment already records this
  ordering, so it is not a defect.
- **XR5: correct, and it pins the at-exit path.** In run_card.py, the quota
  `sys.exit` (l.723) fires before the in-loop check (l.735), and the final check
  (l.777) sets `refs_final`. That leaves `finally`'s `if not refs_final` (l.800)
  as the only reporter, which is X-6-F1-F1's ledger design: every exit closes
  the run, and the ref check rides on it. The row asserts rc 1, the quota
  message, the exact at-exit header line, the absence of both other headers,
  and the full restore line with XR5's own tip. main is reset before and after
  the block, ahead of XR3. My two extra mutants (an inverted guard, and the
  quota exit moved below the in-loop check) both fail only this row.

  exercised. Every R1 row (RF3, RF4, RF11, e2e RF1, RF2 and RF4) puts the ref
