## Ruling: GIT_CONFIG_PARAMETERS refusal-only — accepted
The decision is correct for the gap the card addresses: an inherited
`-c core.fsmonitor=<hook>` that beats GIT_CONFIG_COUNT. The premise reproduces
on git 2.47.3. Every entry point (runner start and scope checks,
check-core-paths, merge-card, promote-pass, audit-merges, queue-check) calls
the same git_state_refuse / git_state_problems. That read keeps the variable,
so the hook is named and the run exits non-zero. Stripping that one key would
need a second quoted-format parser in each language and closes nothing more.
Unsetting the variable blinds the refusal. Unsetting would also close only
the operator-caller channel, and the same keys stay settable in repository
and global config, which are the scopes a worker is likelier to reach than
GIT_CONFIG_PARAMETERS: the deny list covers GIT_CONFIG*.

I checked the other -c keys:
- **Code execution.** core.hooksPath, core.sshCommand, diff.external,
  textconv drivers, filter.* and credential.helper run as the caller who set
  them. That gives no privilege gain, and name-only diffs run no
  textconv/external driver.
- **core.commitGraph.** It can only switch reading of an existing graph file
  on or off. The file itself is X-6-F1-F2-F3.

The card's "fails closed" claim does **not** cover every -c key.
`-c diff.relative=true` (or `[diff] relative` in any config scope) hides
changes from the shell scripts that run from nucleus/v3, as shown below. Two
consequences:
- This is a key-class gap, not a gap in this channel's layering. None of the
  three options fixes it in every scope.
- GIT_CONFIG_COUNT can never neutralise any key against GIT_CONFIG_PARAMETERS.
  A future neutralisation must use an explicit command flag (for example
  `--no-relative`, `--untracked-files=all`) or a refusal read. That is
  X-6-F1-F2-F2-F1. It is pre-existing and outside this card, so it is not an
  ESCALATE.
