## Findings

R1 (blocking): a committed worker deletion of the gate's verdict file is not a
violation. The card branch adds `verdicts/<ID>.md` and the worker then deletes
it in a commit. That leaves no net change in `base...HEAD`, so the file never
appears in `changed_files(wt, base)`, and neither `gate_verdict()` nor the
PROTECTED check ever sees it. Repro (a scratch repo laid out like the
test-enforcement one): gate commit "nucleus v3: RV verdict REWORK" adds
verdicts/RV.md; from there, `git rm verdicts/RV.md; git commit -m "nucleus v3:
RV verdict gone"`; `scope_violations(..., "RV", <gate sha>)` returns `[]`. The
same holds on the base runner, so this is not a regression. But it is the very
"worker reverted a protected file to get past the check" that the card exists
to stop. An uncommitted delete is flagged (git status shows it). Fix inside the
card's limits: in `scope_violations()`, also check the files changed since
pre_head (`changed_files(wt, pre_head)`). At minimum that means
`verdicts/<card_id>.md`; better, every PROTECTED path, since only the gate's
verdict can legitimately differ from base at pre_head. That way a protected
file that existed at pre_head and was deleted or reverted to base is reported.
Add the test "runner: a committed worker deletion of the gate verdict is a
violation", plus a named mutant that drops the new check.

R2 (fix in this rework): the mutant SUBJECT-ANY-CARD (subject check relaxed
to the draft's `" verdict " in subject`) is UNCAUGHT. No scenario has a last
toucher whose subject is a verdict subject for a different card. Add one: a
commit "nucleus v3: OTHER verdict MERGE" that touches verdicts/RV.md, with
pre_head after it, must flag verdicts/RV.md.
