## Summary

This is the P gate, round 2, of rework commit 717cbb19 (on top of de783330 and
the round-1 verdict 2c12f2d3, base nucleus/v3-scaffold 831ea23f). On a separate
detached worktree of 717cbb19, `scripts/gate.sh` passed every step with EXIT=0
and printed `GATE EXIT=0`. `bash scripts/test-enforcement.sh` also passes
there: 58 ok, including all 11 runner verdict scenarios. Scope is correct: only
`tools/run_card.py` (scope_violations, the gate_committed helper and the
pre_head capture in main()) and the new runner section of
`test-enforcement.sh` changed. No other rule is loosened. Style matches the
files.

The rework fixes the round-1 repro: a committed `git rm` of the gate's verdict
is now flagged. It does not deliver the card's stated property, "exempt while
it is exactly as the gate left it at pre_head". The since-pre_head check is a
merge-base (three-dot) diff, so a worker that rewrites history to drop the gate
commit is not flagged. Hence REWORK.

## Round-1 findings

- R1 (committed deletion): fixed only for the descendant case. The repro, with
  test "runner: a committed worker deletion of the gate verdict is a violation"
  and mutant NO-DELETE-CHECK, is caught. A restore to the base version takes the
  same path. A history-rewrite deletion is still not caught; see N1.
- R2 (SUBJECT-ANY-CARD uncaught): fixed. The new scenario catches it, and I
  verified that.
- The author's choice not to flag every PROTECTED path changed since pre_head is
  sound. Any protected path that differs from base at HEAD is already flagged
  by the base diff. A protected path that differs between pre_head and HEAD but
  not between base and HEAD has been restored to base, which is a legitimate
  repair of damage from an earlier run. Only the gate's verdict may differ from
  base at pre_head, so it is the only path that needs the extra check.

## Findings

N1 (blocking): a worker can drop the gate's verdict commit with a history
rewrite, and the check passes. Condition (a) is
`own not in changed_files(wt, pre_head)`, and changed_files diffs
`pre_head...HEAD`, which starts at the merge-base. When HEAD no longer descends
from pre_head, the merge-base drops below the gate commit and the deletion is
invisible. The deletion also leaves no base...HEAD change. So `exempt` is True,
the explicit flag is skipped, and `scope_violations()` returns `[]`. None of
these commands is in the opencode deny list (reset, checkout, stash), and
WORKER-PROMPT does not forbid rebase or amend. I reproduced three variants in a
scratch repo laid out like the test-enforcement one, with the gate commit
"nucleus v3: RV verdict REWORK" = pre_head:
- `git rm verdicts/RV.md; git commit --amend --allow-empty --no-edit` at the
  round start, where the gate commit is the tip.
- `git rebase --onto <gate>~1 <gate>`.
- `git switch -C <branch> <gate>~1` followed by new commits.

The amend path is the realistic one. A worker that runs `git commit --amend` on
its first rework commit actually amends the gate's commit. That keeps the
verdict content but is flagged, because the merge-base moves. The flag is
fail-closed, but it is a false "(protected)" report on an unchanged verdict,
which is exactly what triggered X-6 N1. If the worker then removes the file in
another amend, the check passes.

Fix, inside the card's limits: test (a) against pre_head's tree, not against
the merge-base. For example:
`git diff --no-renames --name-only <pre_head> -- <own>` (the working tree
against the commit, which covers committed, staged and unstaged changes),
together with `git ls-files --others -- <own>`. A non-empty result, or a git
error, means not exempt. In a scratch copy I checked that this closes all three
variants. The plain amend that keeps the verdict content is then correctly
exempt, and all 58 test-enforcement scenarios still pass. Add the test
"runner: an amend or rebase that drops the gate's verdict commit is a
violation". Add the mutant THREE-DOT-PREHEAD (going back to
`changed_files(wt, pre_head)`), which must fail that test.

N2 (fix in this rework): the prefix-ID property has no test. Two mutants are
uncaught:
- ID-PREFIX (`startswith("nucleus v3: <ID>") and " verdict " in subject`) would
  let a "nucleus v3: RV-F1 verdict ..." commit vouch for verdicts/RV.md.
- OWN-PREFIX (`f.startswith(own[:-3])`) would exempt verdicts/RV-F1.md together
  with verdicts/RV.md.

The code under review is correct for X-6 against X-6-F1 in both directions; I
probed it directly. Nothing pins this, though. Add one scenario: a commit
"nucleus v3: RV-F1 verdict MERGE" is the last to touch verdicts/RV.md, so
verdicts/RV.md is flagged. In the mixed verdict-commit scenario, also add
verdicts/RV-F1.md, which must be flagged.

## Also probed (no change needed)

- A rename (`git mv`) of the verdict is flagged, because `--no-renames`
  reports the source path. An uncommitted delete is flagged. A delete followed
  by an untracked identical re-create is flagged (strict, but fail-closed).
  `git revert` of the gate commit is flagged.
- An empty pre_head disables the exemption. A garbage pre_head, such as
  rev-parse error text, makes gate_committed false. Both cases are fail-closed.
- LOG-WHOLE-HISTORY (dropping `base..` from the log range) survives, but it is
  equivalent here. A last toucher that is in base implies that the file is not
  in the base diff unless the worker changed it, and condition (a) catches that
  change.
- skip-worktree hides an uncommitted forged edit of the verdict too:
  `scope_violations` returns `[]`. That is X-6-F1-F2, now confirmed for this
  file.

## Follow-ups

X-6-F1-F1 (runner, core): pre_head is per run, so a forged
"nucleus v3: <ID> verdict ..." commit from an earlier run is exempt on a
`--keep` rerun, including runs that exited before the scope check. Persist a
trust anchor or scope-check on every exit path, and add an end-to-end main()
test with a fake `opencode` so that PREHEAD-PER-ATTEMPT (still UNCAUGHT) is
caught.

X-6-F1-F2 (runner, core, pre-existing): `git update-index
--assume-unchanged/--skip-worktree` hides uncommitted edits from
changed_files(), including edits to verdicts/<ID>.md. Refuse such entries
(`git ls-files -v`), or run acceptance from a clean export of HEAD.

X-6-F1-F3 (runner, core, pre-existing): the opencode bash deny list matches
command prefixes, and it does not cover history rewrites. As the patterns
read, `git rebase`, `git commit --amend`, `git update-ref`, `git switch -C`,
`git restore`, and `git -C . reset` / `git -c k=v checkout` all pass. Deny the
rewrite commands, or rely on a check against the anchored base, and state the
amend/rebase rule in WORKER-PROMPT.
