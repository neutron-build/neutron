- (b) **The added `LoadWaiting` firing in `wait_settled` (`src/buf/pool.rs:869`) is required by the spec**: the I-PIN-CURRENT row's hooks "report where a pin or a creation is about to wait for a load (*waiting*)", and case (f) has the controller record "T3 *waiting* or T3's end". In this card's API a creation's wait is `wait_settled` (`create` returns `Loading`), so that is where the firing belongs. **2. `create`'s freed branch claims the frame in the hold that decides, not after the re-init (the pre-gate's F2). The code's order is right; a pin is a follow-up, not blocking.**
Card Work 8 C4 (line 176) clears `meta.freed` after re-initialising `g`; the code clears it at `pool.rs:827`, under the same mutex hold that found the frame freed. Under the card's order, a second creation of the same freed key that reaches C4 before the first creator's late clear also finds it freed, raises the count and blocks on `g`'s latch. Once the first creator releases, it re-zeroes the page, wiping whatever the first creator wrote, and both are told `Created`. That breaks "makes no second one" (§5.4; I-PIN-CURRENT) in substance. The code's order gives the second creation `Exists`. Confirmed: under this gate's CREATE-FREED-CLAIM-LATE all 48 tests pass, so nothing pins the difference. Not blocking, because no correct caller reaches the case: an LPID's creator took it alone from the allocator under the free-set lock (§4.2, §5.6), and only LPIDs are freed (A-4b), so a MapLeaf's racing restarts never meet a freed frame. A deterministic pin also needs a seam the card's hook table lacks (no point between C4's decision and `g`'s latch). Related, by reading: if `g`'s latch is poisoned, or `init_page` fails after the claim, `meta.freed` is false while the content is still freed. Only poison reaches this. A-3a-F2.

**3. `t_pin_load_race_f` hangs, rather than fails, when the creation's wait is not reported (the pre-gate's F3). Not blocking.**
Reproduced: with the `wait_settled` firing removed, `t_pin_load_race_f` ran past 60 s and was killed at 120 s (exit 124), and `create_vs_loading` passed. The controller waits for T3 *waiting* or T3's end, which is exactly what the spec's case (f) prescribes. A real-thread test cannot tell a silent wait from a slow thread without time, and Limit 6 forbids timed waits. The mutant removes test instrumentation, not protocol: none of the card's 29 mutants or the spec's eight hangs any test; every one fails by assertion (lines 294 and 430 hold for them). Deadlock detection under A-4c0's harness covers this (A-3a-F3).

**4. The pre-gate's F4 (BUF-BORN-LATCHED over-claimed for a reused frame): confirmed, documentation only.** In the freed branch, between the claim (`pool.rs:827`) and `g`'s exclusive latch (`:834`), a stale-name holder can latch `g` and read the old, freed bytes; `is_freed()` is true. The new page itself is never read before `release`, so `create`'s doc sentence holds for the page but not for the frame. The `mod.rs` BUF-BORN-LATCHED text says "enters the table", which the reused frame does not. Also a nit: `HookPoint::LoadWaiting`'s doc says "No latch" for the creation's firing, but a creation may hold its tree's latches there (§5.4 allows it); the pool holds none. Wording goes to A-3a-F2.

**5. A waiter already asleep then does not wake: a poisoned mutex surfaces only to a thread that is woken, so the pre-gate's "no hang follows" is too strong. Nothing in `buf` can panic while it holds the table mutex (every index is a `get`, every counter saturating or checked, no hook runs under it), so `buf` cannot poison the mutex itself. The poison mark and its checks in the wait predicates are A-3c's (card line 37). A-3a-F3 notes it for A-3c.

**6. The pre-gate's F6 (`as` casts in tests): dismissed.** `tests/buf_pin.rs:575, 714, 1250` cast small constants that cannot truncate; Limit 8's rule is about casts that can.

**Liveness mutants.** LOAD-NO-NOTIFY hangs a real-thread test (pre-gate `OWN-E`, checked), and WAIT-NO-RECHECK passes the whole suite (`OWN-F`, checked). Both belong to A-4c0's harness and A-4c's exploration, as the card says, with one addition. WAIT-NO-RECHECK is also a safety fault, not only a liveness one: the pool has one condition variable and notifies all on every load's end, so a waiter woken by another key's load would find its frame still `Loading` and return `Invalid`. Whether the waiter is already asleep at that notify is a schedule question that hooks here cannot place, so the harness needs that schedule (A-3a-F3).
