## Re-attack: does entry-first open a hazard?

- **Unreachable-but-mapped root at a cut: no, as written.** The removal and the frees are in one gate hold. A flip lands before or after both, and the epoch-`k` copies of the directory leaf and MapLeaf keep image `k` closed.
- **Leak on crash: no.** A crash keeps the last image, where the entry and the mapped pages agree, and the walk resumes at step 6.
- **Reuse: closed.** Each free follows the removal of its last reference, and a path is freed top-down, so no mapped page or entry names a freed LPID, in memory or in an image.
- **Replay: no change.** A replayed `DropTree` finding the id absent does nothing. Every write to the tree has ts below `D`, and the walk needs `W > D` with `W ≤ M`, so none replays into an absent tree.
- **The failure direction did change, and that is N1.** If an implementation restarts after the removal, the image holds no entry and a mapped root. That is a silent leak with nothing left to walk it, where free-first gave a refused open. It costs space, not data, but nothing finds it unless amcheck runs, and §14 step 7 makes amcheck optional.

## The Goal's claim: true and bounded, with two notes

The last step reads no page under the gate. A non-resident page restarts it before its first mutation, so a flip is held for at most one directory descent over pinned pages. Chains go earlier, one per gated operation. A drop costs (chain-bearing entries + leaves) gated operations. Restarts are not bounded by count, but each one releases the gate, so they cannot stall a flip.
- **§6.5's directory pack breaks the claim if it runs inside the step (N3).**
- **The claim counts reads, not latch waits (N4).** The step's exclusive directory-leaf latch waits for threads coupling through that leaf, each of which waits on one root latch.

## Findings

**N1. The test cannot reach entry-first's own failure.** DROP-RESTART-MID-OP is "the last step mutates, meets a non-resident directory page". Under entry-first, the first mutation is on the directory leaf itself, so no directory page is left to meet (except N3's sibling), and the pre-mutation restart the fixture's evicted page causes is legal. The realistic bug is a forgotten pin: the entry is removed, then the root's MapLeaf or an emptied page is non-resident, and the step restarts. `t_drop_every_cut`'s fixture evicts neither, so that path never runs. `t_drop_step_shape` misses it too: the hook sees two gated operations, neither wrong alone. The unlink step has the same hole.

**N2. The restart rule collides with the split path.** It is stated universally, and draft 6's text assumed otherwise.
- **Prune.** §6.4 and §10.3 run the prune first, and a split "only if the prune did not free enough room". The prune is a mutation, so a restart after it is now forbidden, although it would be harmless: the graph is closed. So the split's reservation must precede the prune. Nothing says so.
- **LPID allocation.** §5.6 counts an allocation as a mutation, and the MapLeaf of the allocated LPID is not known before it. A split holding its parent exclusively that allocates into an evicted MapLeaf has no legal move: §5.3 forbids the read, §5.6 the restart. A legal shape exists (take the LPIDs under the free-set lock only if their MapLeafs are resident, and pin them, or else restart), but an implementer must invent it, on the hottest write path. The "CreateTree" and "Building" sentences depend on it as well.

**N3. §6.5 lets a directory removal pack.** §6.5 says a directory removal "may pack" the leaf while holding its parent. §6.8's pin list omits the parent and the neighbour. Pinning them overruns §5.4's quota: three directory pages plus a tree path of `height` is height + 3 against height + 2. Latching the directory neighbour after the root would also break I-LATCH. One sentence closes it: the last step does not pack, and a later gated operation may.

**N4. Root names leave the latch mode and a stall coupling open.** §6.2 has writers couple exclusively, and §6.8 calls the directory leaf the root's parent, so a literal reading has every writer latch the directory leaf exclusively. Say shared, unless the operation changes the directory. Separately, a coupling thread holds the directory leaf while it waits on a root latch, which a positioned cursor (§6.6) or a leaf root's chain operation can hold. A directory writer then queues on the leaf, and a writer-preferring lock makes every other tree under that leaf queue behind it. Using `try_latch` on the root, and otherwise releasing the leaf and re-descending, keeps the rule without that coupling.

**N5. Seven of my spec mutations pass the greps.** G2 and G3 matter most: they remove the restart rule's force and the last step's pin list while the anchored prefixes stay. By reading, the text at this tip is right, so this does not block. S-1-F7-F2's Acceptance should pin them.

**N6. `R_MAP` and `R_EPOCH` (for R-1).** §6.8 charges up to `height` new MapLeaf pins per step to `R_MAP`, but §5.4 sizes `R_MAP` for dirty pages only. §5.4's `⌈dirty frames / 510⌉` also reads as a lower bound: scattered dirty pages can pin one MapLeaf each. That predates this card. Separately, §5.6's "two claims per thread" assumes recording an evicted copy never first-touches a further MapLeaf. R-1 must derive that depth rather than quote it.

## Barring root caches: the cost

Yes, it is worth flagging. It needs no owner decision now.

Measured on E0's B+tree, in memory, with point gets: a cached root against a directory get plus the tree get. n5000, median of 5 interleaved runs, on a loaded shared machine (load 9–17), so treat these as rough.

| Threads | 10 trees, 200 directory entries, M ops/s (cached → directory) | Ratio | 1 tree, 2000 directory entries, M ops/s (cached → directory) | Ratio |
|---|---|---|---|---|
| 1 | 0.65 → 0.56 | 1.16× | 0.90 → 0.74 | 1.21× |
| 4 | 1.96 → 1.35 | 1.46× | 0.82 → 0.78 | 1.05× |
| 8 | 2.46 → 1.62 | 1.51× | 0.55 → 0.55 | 1.01× |
| 16 | 3.04 → 1.46 | 2.08× | 0.52 → 0.53 | 0.99× |

**How to read it.**
- **Single thread:** about +240 ns per operation, 16–21% of a bare point get. That number is the solid one.
- **Scaling:** the left column gives each tree its own pool, so the directory's pool is the one shared point. The right column's single data pool is already saturated by E0's page-table mutex, which hides the directory. So today the cost is hidden by a worse bottleneck, and once §3.12's optimistic latches remove that bottleneck, the directory becomes a global contention point, as the left column suggests. The left column overstates a real single-pool store, but I would expect a real slowdown there, on the order of 1.5× at 16 threads for many-table loads. That figure is an estimate, not a measurement.
- **Model limits:** the directory get allocates a value (overstates), and it drops its latch before the root's (understates).
- **In context:** for a full SQL statement this is small, likely low single digits of percent at most; it matters for the KV path and E7/E9 scaling.

**The bar is wider than safety needs.** C-T6 §7.5 proves a tree cannot be dropped while any registered snapshot can see it, and apply writes precede `D` (with `W ≤ M`). So a foreground operation could keep a root LPID for its statement, safely. Only background jobs (sweeps, abort cleanup) need the rule. Recommendation: keep the rule now, since it is simple and it is what the evidence covers. S-1-F7-F2 records this as a §19 known cost with a trigger: directory latching above 5% of point-op CPU, or below the §3.12 scaling bar at 16+ threads, opens a spec edit allowing a root name for the life of a registered snapshot.
