## Findings

### R1 (blocking): the eol exception lets a forged blob through and changes the gate result
The exception accepts a mismatch when `check-attr -a` reports only `text`/`eol`/`crlf` and `hash-object --path` equals the id. That hash runs through the clean conversion, which is many-to-one: CRLF and LF both clean to LF. The repository's root `.gitattributes` is `* text=auto eol=lf`, which puts **every** text file under the exception. For those files smudge is the identity, so a blob forged to hold the true content with `\r` inserted before some LF has these properties:
- it checks out byte for byte;
- it fails the `--no-filters` hash;
- it cleans back to the true content, so the exception accepts it.

`hash-object` does not load the index, so git's has-CR-in-index guard for `text=auto` does not apply.

**Reproduced** with the card's script, extracted from b6d4ba76, in a /tmp repository with the same `.gitattributes`:
- `gate.sh` sources `conf.sh` (`STRICT=1`, LF) and fails when STRICT is 1;
- the honest run ends `GATE EXIT=1`;
- after overwriting conf.sh's loose blob with `STRICT=1\r\n`, fresh-gate prints `fresh-gate: 1 file(s) matched through their eol conversion` and the gate runs the CR bytes (`STRICT` is now `1\r`) and ends `GATE EXIT=0`, exit 0.

This needs no config, hook or attribute file: it is FG11's own threat, a swapped loose blob. In bash scripts a trailing CR changes values and commands. FG11b did not catch it because its forgery replaced the whole content.

**Fix (script):** allow the exception only when the path's `eol` attribute is `crlf`, and the working file has no lone LF. For an `eol=crlf` path, a forgery that adds CRs checks out to the same bytes as the honest blob, so it is harmless. Refuse every other mismatch. In this repository that keeps the two `.ps1` files (and any `.bat`/`.cmd`) and nothing else.

**Rows (forged-object):**
- **FG11c:** a `\r`-before-LF forgery of a `text=auto eol=lf` file is refused.
- **Mutant FG-EXCEPTION-LF:** the old attribute-only rule, which FG11c must catch.

### R2 (blocking, card text, P amends; not the worker): the Notes' GATE-PROMPT replacement can be redirected
The extraction checks only the leaf: the extracted blob against the id that `nucleus/v3-scaffold:path` resolves to. Both reads go through the same commit and tree lookup.

**Reproduced:** one `git replace <scaffold> <evil commit>` made the Notes' loop, run verbatim, extract the evil `fresh-gate.sh`, with no `EXTRACT FAILED`. By the X-6-F1-F2-F3-F1 argument, a forged scaffold tree or a forged commit-graph does the same, because the planted blob hashes honestly.

**Use instead:** a shallow `--no-local` clone. index-pack re-hashes every received object, and no replace ref or commit-graph travels. It takes about 3 s on the real repository, and it extracted the honest file in the replace-ref probe:
```
fg=$(mktemp -d) && GIT_NO_REPLACE_OBJECTS=1 GIT_GRAFT_FILE=/dev/null git -c core.hooksPath=/dev/null -c advice.graftFileDeprecated=false clone -q --no-local --depth 1 --no-checkout --single-branch -b nucleus/v3-scaffold "file://$HOME/Workspace/neutron-v3" "$fg/c" && git -C "$fg/c" rev-parse HEAD && for f in fresh-gate.sh git-env.sh; do git -C "$fg/c" cat-file blob "HEAD:nucleus/v3/scripts/$f" >"$fg/$f" || { echo "EXTRACT FAILED: $f"; break; }; done
```
- Any `EXTRACT FAILED` line, or a failed clone, stops the gate.
- Record the printed scaffold id.
- The ref itself stays trusted, as everywhere else.
