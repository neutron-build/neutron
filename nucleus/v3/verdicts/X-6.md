## Findings

R1 (blocking): the SIGKILL path is a no-op. `browserProcessOf()` returns
`context.browser()?.process?.()`, and for `launchPersistentContext` that is
`null` in all three engines. The gate confirmed this with a standalone probe,
and an instrumented scratch copy printed `killed=false proc=false` on every
`sigkillBrowser()` call. As a result:
(a) T2 phase 3 ("browser SIGKILL") and all of T3 ("unflushed, then SIGKILL")
were in fact graceful `context.close()` calls;
(b) on a scenario timeout the harness cannot kill a hung browser. The gate
SIGSTOPped Chromium under `--step-timeout-ms=8000`: the `Promise.race` did
fire and the run went on, but the stopped process was reaped only by
Playwright's own exit handling, never by the harness;
(c) the `closeBrowser()` backstop and the `process.on('exit')` kill are no-ops
for the same reason.
Fix: find the browser PIDs another way (for example `pgrep -f` on the
per-run profile directory, which is unique), SIGKILL them, record
`killed`/`pids` in results.json, and mark the scenario `error` if no kill
happened.

R2 (blocking): the README and RESULT state what was not done. The "T2
browser SIGKILL" column, the T3 "unflushed writes survived a SIGKILL" headline,
the "persistence across a WebKit process kill" line and "SIGKILL on overrun"
all describe a method that never ran. After R1, re-run the full datasets and
correct the README. Gate evidence: in a scratch copy with real PID-based
SIGKILL (1–2 PIDs killed per kill), `--quick` across all three engines still
gave T2 browser_kill ok (0 missing, 0 corrupt, WAL 21 B) and T3 60/60 pages
plus a 20 B WAL. The numbers are expected to stand; the record must still
come from a real kill.

R3 (blocking, small): WAL content is never checked. The `wal_len` read back
after reopen is `getSize()`, so the T1/T2/T4 checks are length-only. M1, which
writes zeros of the right length, passes everything. The card's goal is to
"persist pages and a WAL". Add a WAL read-back (for example a worker-side
read through the WAL handle, compared against the expected records) and check
it in T1/T2/T4.

R4 (doc, fix with the rework): M5, `flush()` as a no-op, passes every test.
That is inherent: process death leaves the OS page cache intact, so this
harness cannot show that flush is load-bearing. The README's decision section
should say so explicitly, i.e. that PASS shows survival of process death, not
that flush is effective. Also, the `lib.rs` module doc says "Data written
before a *successful* `flush` is not guaranteed to survive a kill". That reads
backwards; it presumably means "only data flushed successfully is guaranteed".

Non-blocking notes for D-5b (not separate cards): `WalCursor::append`
advances the frontier before the write. A failed write therefore leaves a hole
and the cursor ahead of the file. The spike tolerates this, but the production
`OpfsEnv` must not. Exit code 0 on DECISION FAIL is a documented choice and
is acceptable.
