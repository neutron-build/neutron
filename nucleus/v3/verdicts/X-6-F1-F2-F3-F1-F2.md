   - `verify_objects`' set;
   - the commits of `rev-list --boundary base..tip` (marker stripped);
   - every tree under each of those commits (`--no-walk --stdin`).

   A path-limited log reads only those commits and their trees, and only through
   the same object store. If a forged tree has content that leads to other trees,

## Ruling 2: the EXCLUDE-FORM shared-subtree case is not a residual risk
The production code uses `--no-walk` over the commits, so the code has no gap.
The question is only whether a fixture should pin the mechanism. For
`gate_committed` to lie True, the reads at f must be the same from the gate
commit G to the tip. The tip is honest (it is in the floor set). So one of G's
own trees on f's path must be forged. Each of those trees transitively contains
the gate's verdict blob, which holds a fresh `Commit:` id. Such a tree is
reachable from a scaffold boundary commit only if the scaffold already contains
that exact directory.

The exclusion form omits trees reachable from boundary commits, and boundary
trees that are base or merge bases are already in the floor. So no realistic
state lets that omission produce a True lie. A forgery of a shared tree that
does not touch G's trees can only hide a change and revert it, which leaves the
gate's content at f. The (e'''') catch is legitimate and fails loudly: a
refactor that drops `--stdin` makes the shim miss the listing, and the row then
FAILs (True on OJ). No follow-up fixture.
